## Implemented Behavior

- Tabs: Profile, Settings, Matches, Connect. The old Bluetooth URL redirects to Connect and is hidden from the tab bar. Initial signed-in entry goes to Profile.
- Latest UI cleanup removes the readiness checklist from every route, and removes answer transcripts, predictor-summary headings and long explanatory text from Profile. Inputs and approved matching controls remain. Saved answers/evidence and backend eligibility/`profileReady` validation are unchanged. Evidence excerpts remain available during initial onboarding review, not on Profile.
- Matching consent exists only in Settings and uses the existing authenticated `/v1/consents` receipt/revocation path. New onboarding saves without changing consent and hands off to Settings before discovery permissions. Legacy initial onboarding can still submit an explicit choice. Profile edits and repeated onboarding saves preserve current server consent even if an older client sends a stale boolean. No profile save can implicitly opt an existing user in or out. Preview, radius and Muse settings are likewise preserved on Profile save.
- Settings retains the existing Core2Badges, OptionalDevices and signout/revocation code. It contains preview sharing, separate location/Bluetooth switches, radius and Muse description opt-in, plus existing account/integration controls. The navigation commit does not change device API or firmware behavior; required existing device code is isolated in the prerequisite commit.
- Matches uses an additive `GET /v1/connections/page` RPC-backed query. Projection/redaction happens before full-set search, relevance ranking and filtering. Pages have six entries, stable created-time/ID tie breaks, totals, clamped page numbers and disabled ends. It does not search the legacy capped-100 fetch. Legacy `/v1/connections` remains unchanged for older/device clients.
- Like/Dislike writes a distinct private `match_preferences` table keyed by actor, peer and both profile versions. Idempotent updates do not create invitations, outcomes, training labels, location opt-ins or AR display permissions. Owner-only RLS reads; writes and actor-parameterized RPCs are service-only. Accepted-conversation outcome controls remain separate.
- Connect consumes canonical recommendations from `GET /v1/discoveries`, merges location/BLE results by directional profile-version event key, and never treats a raw radio signal as a match. The GPS radius can be reduced from the existing two-mile maximum to 0.1 miles. Bounds and radius filtering are enforced server-side, including invitations; BLE eligibility does not use this radius.
- One authenticated DiscoveryProvider owns timing. A banner lasts five seconds, transient cards expire sixty seconds after first admission to the discovery surface, and repeated polls/token rotations/source changes do not restart either. A bounded queue avoids notification floods. Only event hashes and first-surfacing times are persisted locally, partitioned by actor/profile version. Expired-event tombstones prevent immediate replay, including reloads. A new profile version can qualify again. Background clears visible data; fresh responses are required after resume. No saved connection or preference is deleted by expiry.
- New-match popup shows only the approved preview, independent private rating controls, and a separate invitation action. Fuller facts appear only in mutually accepted connection cards through the authorized projection.

## Muse and Maps

Muse uses the already configured server-side Meta provider (`MUSE_API_KEY`, `MUSE_MODEL`) and never a frontend key. Both users must separately enable `muse_descriptions_enabled`. This is independent of matching, meetup and headset display permission.

The supported description basis is deliberately narrow: an exact common preview interest backed on both sides by confirmed matching-enabled facts with valid answer citations. Fact IDs and evidence references are checked internally; only opaque citation aliases and the approved topic go to Muse. No private answer, fact details, inferred trait, Spotify or Instagram material is sent. The provider response must satisfy bounded schema, exact citations and a finite safe wording grammar. Unsupported claims are rejected. No template is returned as successful Muse output when generation is unavailable or fails. A current score does not contain a causal fact trace, so the UI identifies a supported shared topic without claiming it is the exact causal model explanation. Matches without such a disclosure-safe topic show an honest unavailable state. Cache is bounded, keyed by actor/profile/preview/permission context, revalidated after generation and before every response. Tests use only fictional fixtures and mocked provider HTTP; no real model calls were made.

Google Maps reads only the existing `/v1/connections/{id}/location` projection. That SQL requires mutual acceptance and both independent location-sharing opt-ins and applies lease/freshness limits. The UI removes points on stop, background, stale lease, auth change or revoked connection. Each sharing poll rechecks local foreground permission without prompting; withdrawal hides coordinates by the next poll (ten seconds maximum under normal scheduling). A delayed response cannot revive stopped/unfocused sharing. Two nodes and a straight connector are shown; no routing/direction claim is made.

Web renderer: Maps JavaScript API, loaded only after authorization. Supply `EXPO_PUBLIC_GOOGLE_MAPS_WEB_KEY`, restricted to the permitted web origins and Maps JavaScript API. No key is supplied in this snapshot; setup-required and stop-sharing states were tested, not live Google tiles.

Native renderer: SDK-54-compatible `react-native-maps@1.20.1`, explicitly `PROVIDER_GOOGLE`. Supply `GOOGLE_MAPS_IOS_API_KEY` and/or `GOOGLE_MAPS_ANDROID_API_KEY` at build time. Config binds them to `ios.config.googleMapsApiKey` and `android.config.googleMaps.apiKey`. Restrict the keys to the appropriate bundle/package and Android signing certificate. Build a new development binary with the native module; the source was typechecked, but no native binary/device was built or tested. No Google project, billing or paid API was enabled by this task.

The existing Leaflet web map and native OpenStreetMap external link remain intact. They are exposed only as an explicit, correctly labeled fallback after the same location authorization; the app never silently labels them Google Maps.
